# v0.6.0-rc.2 — Owner-operated backup design candidate

This candidate adds a strict, non-activating owner policy for the storage, capacity, schedule and key-custody decisions that sit between synthetic Phase 5 recovery evidence and production adoption.

## Included

- A machine-readable owner policy example for all six Phase 5 modules.
- Offline validation requiring two distinct off-host repositories and two separate offline recovery-key devices.
- Capacity, RPO/RTO, staggered schedule, hidden-task, notification and recovery-drill controls.
- A deterministic private plan with a redacted terminal representation.
- Focused tests for storage separation, secret rejection, disabled scheduling, capacity, retention and readiness decisions.
- Owner documentation and a host-reconciliation record that does not disclose private paths or modify existing tasks.

## Deliberately excluded

- Task Scheduler registration or modification.
- Repository creation, production backup, key generation or key rotation.
- Object storage, SFTP or replica-copy implementation.
- Adoption of existing backup scripts.
- Stable `0.6.0` or production-readiness approval.

## Release decision

Go for `0.6.0-rc.2` only after the exact commit passes the standard cross-platform validation matrix. The existing `v0.6.0-rc.1` integrated recovery workflow evidence remains applicable because this candidate does not change the six application/vault implementations or their workflows.

No-go for stable `0.6.0` until owner media and key custody are established, scheduling/alerts are implemented and reboot-tested, replica transport works, and representative production data is recovered on an isolated environment.
