# v0.5.0-alpha.2 — Isolated Uptime Kuma

Second bounded Phase 4 prerelease. **Phase 4 is not complete.** This does not migrate or replace an existing Kuma installation and is not a production-ready multi-application installer.

## Delivered

- Separate `kuma plan/up/status/stop/remove/seed/inspect-monitors/fixture-down/fixture-up/backup` interface and explicit recovery plans.
- Digest-pinned Kuma 2.5.5, local-engine binding, cached-image-only execution, loopback publication, dedicated bridge with outbound access and no Docker socket.
- Two synthetic HTTP monitors, generated private account and an explicitly selected one-monitor status page. Repeated registration preserves IDs and refuses foreign definitions.
- Ownership/drift/attachment guards, private files, process locking, exact-plan confirmation and data-preserving removal.
- Whole-data stopped-state snapshots with hashes, SQLite/content validation and recovery into a fresh independent volume/project. Credentials and history are preserved; snapshots are sensitive and **not encrypted**.
- [Commands, troubleshooting and precise limitations](../kuma-module.md).

## Validation evidence

Live Windows Docker Desktop, local Linux amd64 engine, synthetic data only:

- Fresh setup and repeated seeding preserved exactly two monitor IDs and selected only the fixture for the public status page.
- Deliberately stopping only the fixture produced a down heartbeat and rendered **Degraded Service**; starting it again restored **All Systems Operational**. The Kuma self-check remained up. No external notification-delivery test was performed.
- Stop/start preserved container identity, authentication, monitor IDs and history. Repeating `up` preserved identity and startup timestamp.
- A stopped backup contained two monitors, one user, one status page and **34 heartbeats: 10 down, 24 up**. Integrity and private permissions were checked.
- A new project/root/port restored that snapshot; saved credentials authenticated, original monitor IDs and down/up history remained, and the selected status page rendered correctly. New polling naturally adds heartbeats after restoration.
- Point-in-time active sample with two 20-second HTTP checks: Kuma **149.7 MiB / 512 MiB**, **0.41% CPU**, 12 processes; fixture **8.777 MiB / 64 MiB**, **0.00% CPU**, eight processes. Kuma Docker health was healthy. This is not a long-duration idle/load benchmark.
- The optional `nscd` startup warning under the read-only root did not prevent the tested HTTP/DNS paths. Other monitor types are not certified.
- Trials are stopped and their exact owned containers/networks removed after validation. Private files, the snapshot and both data volumes are retained. No existing production container, monitor, public status page or domain configuration was modified.

The suite adds **31 Kuma regressions** to the previous 152 tests, covering mocked Docker ownership/lifecycle, real private filesystem checks and SQLite snapshot tampering/content/recovery cases. CI tests Windows/Linux/macOS on Python 3.12 and 3.14; it does not run application containers. Review the exact release commit's six-job result. Private paths, engine identities, credentials and databases are not published.
