# v0.5.0-rc.1 — Phase 4 integrated candidate

This release candidate combines the separately validated visibility and utility adapters. It is not a full homelab installer, does not enable application execution through the general planner, and does not adopt existing deployments.

## Included

- Glance isolated lifecycle plus reusable seven-page operations layout and privacy-filtered collectors.
- Uptime Kuma isolated lifecycle plus bounded desired-state HTTP monitor, status-page and webhook/SMTP configuration.
- Beszel restricted hub/agent lifecycle and recovery plus a separately gated Windows existing-agent adapter.
- Stirling-PDF isolated lifecycle, real PDF rotation exercise and stopped-volume recovery.
- Portainer with explicit `isolated-engine-only` permission, a disposable nested engine and no host Docker socket.
- One offline integrated validator: `python tools/validate_phase4.py`.

All images are pinned by exact digest for the declared amd64 evidence. Digest pinning supports reproducibility; it is not a guarantee that an image is vulnerability-free.

## Safety model

- Every module uses a separate reviewed plan, project identity, ownership labels and lifecycle boundary.
- Mutating operations require the exact full plan identifier; Portainer additionally requires the literal isolated-control grant.
- Existing services are never discovered and adopted as candidate state.
- Localhost publication is not authentication. Public access remains a later phase.
- Backups contain sensitive state and credentials. Local permission checks and hashes are not encryption or off-host disaster recovery.
- Portainer controls only its nested disposable daemon. Host-socket access remains deliberately unsupported.

## Evidence and limitations

Windows Docker Desktop Linux-amd64 trials cover real application operations and independent recovery for the declared narrow paths. See the [combined record](../validation/phase4-integrated.md) and each linked module record for exact results.

The final local candidate suite passed **294 tests with two expected platform skips**. Repository structure, the integrated Phase 4 contract, Python compilation, Kuma client syntax and whitespace checks passed. Publication review is repeated against the final staged index, and the prerelease tag is created only after the exact pushed commit passes GitHub Actions.

The stable `0.5.0` decision remains **no-go**. The authenticated Beszel chart, native Windows controlled state/reboot acceptance and platform-runtime decision remain open. Python CI on Linux/macOS does not establish Docker application support on those platforms.

## Candidate review commands

```sh
python tools/validate_repository.py
python tools/validate_phase4.py
python tools/check_publication.py
python -m unittest discover -s tests -v
```

Also run `node --check modules/uptime-kuma/configure.cjs`, Python compilation for public source files, `git diff --check`, and review staged content manually before creating a tag. No tag or remote release should be created from an uncommitted or partially staged tree.
